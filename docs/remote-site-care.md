# ระบบดูแลเว็บไซต์ระยะไกล (Do Action: Care)

เอกสารนี้อธิบายระบบที่มีอยู่จริงตอนนี้: portal สั่งอัปเดตปลั๊กอิน ธีม และ WordPress core ของเว็บลูกค้าจากระยะไกล
โดยมีปลั๊กอิน **Do Action: Care** (เวอร์ชันปัจจุบัน 0.5.3) ติดตั้งอยู่บนแต่ละเว็บ

> แผนตั้งต้นของระบบอยู่ที่ [remote-care-plan.md](remote-care-plan.md) ส่วนเอกสารนี้คือสิ่งที่ใช้งานอยู่ตอนนี้

## หลักการ

- **แอดมินเป็นคนกดเท่านั้น** ระบบไม่อัปเดตอะไรเอง รวมถึงปลั๊กอิน Do Action: Care ของเราเอง
- **เว็บเป็นฝ่ายดึงงาน** portal ไม่เคยส่งคำสั่งเข้าไปที่เว็บ แค่ "ปลุก" ให้เว็บมาถามหางาน
- **ทุกคำขอเซ็นด้วย HMAC** ทั้งสองทาง และกันการส่งซ้ำด้วย nonce
- **พังต้องย้อนกลับ** สำรองไฟล์ก่อน ตรวจหน้าเว็บหลังอัปเดต พังก็คืนไฟล์เดิม
- **ปลั๊กอินหลักกับส่วนเสริมอัปเดตเป็นชุด** แล้วตรวจครั้งเดียวตอนจบ

## ภาพรวม

```
แอดมิน ──(กดอัปเดต)──▶ Portal (Cloudflare Worker + D1)
                            │  1. บันทึกงานลง site_jobs (status = queued)
                            │  2. ปลุกเว็บ ──▶ relay บน OVH ──▶ เว็บลูกค้า /?rest_route=/doaction-care/v1/wake
                            ▼
                 เว็บลูกค้า (ปลั๊กอิน Do Action: Care)
                            │  3. ส่งข้อมูล (heartbeat) + ขอรับงาน (jobs/next)
                            │  4. สำรอง → อัปเดต → ตรวจหน้าเว็บ → ย้อนกลับถ้าพัง
                            │  5. รายงานผล (jobs/report) + ส่งข้อมูลใหม่
                            ▼
                 Portal: อัปเดตสถานะ, ใส่รายงานรายเดือน, แจ้งเตือนถ้าพัง
```

## ขั้นตอนการทำงาน

### 1. จับคู่เว็บ
แอดมินสร้างรหัสจับคู่ในหน้ารายละเอียดลูกค้า → กรอกในหน้าตั้งค่าปลั๊กอิน → portal ออก `site_id` กับรหัสลับให้
ที่อยู่ portal ถูกกำหนดตายตัวในปลั๊กอินเป็น `https://portal.doaction.co.th`

### 2. ส่งข้อมูล (heartbeat)
ปลั๊กอินส่งรายการปลั๊กอิน ธีม เวอร์ชัน อัปเดตที่รอ, PHP/WP, พื้นที่ดิสก์ และสถานะ backup ตามรอบ (ดู [รอบเวลา](#รอบเวลา))
portal ตอบกลับว่ามีงานรออยู่หรือไม่ (`jobs_waiting`) และข้อมูลสำหรับกล่องใน wp-admin

### 3. แอดมินสั่งอัปเดต
- รายการอัปเดตเริ่มต้นแบบ**ไม่ติ๊กอะไรเลย** มี "เลือกทั้งหมด" และ "เฉพาะที่ไม่ใช่ Major"
- ติ๊กปลั๊กอินหลักแล้ว ส่วนเสริมในตระกูลเดียวกันจะถูกติ๊กให้ด้วย (แก้ออกได้)
- เลือก "เริ่มทันที" หรือ "ตอนกลางคืน (01:00–05:00)"
- สั่งได้เฉพาะรายการที่เว็บแจ้งว่ามีอัปเดตจริง และไม่ติดเงื่อนไข PHP/WP

**สั่งไม่ได้เมื่อ:** กด "หยุดทั้งหมด" อยู่, เว็บขาดการติดต่อเกิน 3 ชม., เว็บปิดการแก้ไขไฟล์ (`DISALLOW_FILE_MODS`), สัญญาลูกค้าหมดอายุ

### 4. ปลุกเว็บ
portal เซ็นคำขอแล้วส่งผ่าน **relay บน OVH** (`https://51-79-223-252.sslip.io/wake`) ไปที่เว็บ

ทำไมต้องมี relay:
- Cloudways/nginx ของลูกค้าบางเจ้าบล็อกคำขอจาก Cloudflare Worker (403)
- Worker เรียกชื่อโดเมนใต้ `doaction.co.th` เองไม่ได้ (วนลูป 308) จึงใช้ชื่อ sslip.io ที่อยู่นอก Cloudflare

ถ้าปลุกไม่สำเร็จ เว็บยังรับงานได้จาก:
- รอบ heartbeat ทุก 15 นาทีเมื่อมีงานรอ
- ผู้เข้าชมเว็บ: หน้าเว็บที่มีคนเปิด (ไม่ใช่หน้าที่ถูกแคช) จะรับงานให้ ไม่เกิน 5 นาทีครั้ง หลังส่งหน้าให้ผู้เข้าชมแล้ว
- ปุ่ม "ส่งข้อมูลและรับงานอัปเดต" ในหน้าตั้งค่าปลั๊กอิน

### 5. อัปเดตบนเว็บ (`class-runner.php`)
แต่ละรอบทำงานได้ไม่เกิน 60 วินาที ถ้ามีงานเหลือจะขอ portal ปลุกรอบต่อไป (`jobs/continue`)

**ปลั๊กอิน/ธีมทีละตัว**
1. ตรวจหน้าเว็บก่อน ถ้าพังอยู่แล้ว ไม่แตะ (และแจ้ง portal ว่าเว็บพัง)
2. zip โฟลเดอร์เดิมไว้ที่ `wp-content/doaction-care-backup/` (เก็บ 7 วัน)
3. บันทึกจุดกู้คืน (`doaction_care_pending_restore`) เผื่อ PHP ถูกตัดกลางทาง
4. อัปเดตด้วย upgrader ของ WordPress และเปิดใช้งานกลับเหมือนเดิม
5. ตรวจหน้าเว็บผ่าน HTTP (หน้าแรก, `/wp-login.php` และหน้าทดสอบที่ใช้ token)
6. พัง → คืนไฟล์จาก zip → ตรวจซ้ำ

**ปลั๊กอินหลักกับส่วนเสริม (ชุด)** เช่น GreenShift + GreenShift Query, Fluent Forms + Pro, EDD + edd-*
สำรองทั้งชุด → อัปเดตทั้งชุด (ตัวหลักก่อน) → ตรวจครั้งเดียว → พังก็คืนทั้งชุด
(อัปเดตตัวหลักตัวเดียวเคยทำ doaction.co.th พัง เพราะส่วนเสริมเวอร์ชันเก่าไม่เข้ากัน)

**WordPress core** อัปเดตได้แม้ไม่พบ backup (บันทึกไว้ใน log) แต่**ย้อนกลับอัตโนมัติไม่ได้**

**ข้อจำกัด:** ย้อนกลับได้เฉพาะไฟล์ ถ้าปลั๊กอินแก้ฐานข้อมูลตอนอัปเดต การคืนไฟล์อาจไม่พอ

### 6. รายงานผล
สถานะงาน: `queued` → `running` → `succeeded` / `rolled_back` / `failed` / `cancelled`

ถ้าเว็บยังพังหลังย้อนกลับ หรือพังอยู่ก่อนเริ่ม:
- portal ยกเลิกงานที่เหลือของเว็บนั้นทั้งหมด
- แจ้งเตือนแอดมินในระบบ + Telegram (ไม่เกินชั่วโมงละครั้งต่อเว็บ)

### 7. ใส่รายงานรายเดือน
งานที่สำเร็จและ**เวอร์ชันเปลี่ยนจริง**จะเข้ารายงานของเดือนนั้นอัตโนมัติ (แม้รายงานเผยแพร่แล้ว)
- ไม่รวมปลั๊กอิน Do Action: Care ของเราเอง และงานที่ "ไม่มีอัปเดตแล้ว"
- งานจากเดือนก่อนที่ยังไม่เคยเข้ารายงาน (ย้อนหลัง 90 วัน) จะเข้ารายงานถัดไป พร้อมวันที่ "ทำเมื่อ …"
- งานซ้ำ (ชื่อ + เว็บเดียวกัน) ขึ้นบรรทัดเดียว
- เว็บในเครือไม่มีรายงาน

## รอบเวลา

| อะไร | ความถี่ |
|---|---|
| heartbeat ปกติ | ทุก 1 ชั่วโมง (WP-cron) |

| ปลุกผ่านผู้เข้าชมเว็บ | ไม่เกิน 5 นาทีครั้ง (PHP-FPM / LiteSpeed เท่านั้น) |

| ปุ่ม "รีเฟรชข้อมูล" | รีเฟรชทุก 3 วินาทีจนข้อมูลมา ไม่เกิน 90 วินาที |
| cron ของ portal | ทุก 15 นาที: งานค้าง running เกิน 20 นาที → failed, งาน queued ไม่ถูกรับเกิน 24 ชม. → cancelled |
| ปลุกซ้ำเว็บเดียวกัน | ไม่เกินนาทีละครั้ง |

## MCP (ใช้ผ่าน Claude)

| เครื่องมือ | ประเภท |
|---|---|
| `list_sites`, `get_site_updates`, `list_site_jobs`, `get_job_log`, `sites_needing_attention` | อ่านอย่างเดียว |
| `queue_updates`, `stop_site`, `wake_site` | สั่งงาน ต้องส่ง `confirm: true` |

- `queue_updates` ใช้เงื่อนไขเดียวกับหน้าเว็บ และต้องใส่ส่วนเสริมครบทั้งตระกูล
- คำสั่งกำกับใน MCP บอกให้ Claude แสดงรายการและรอแอดมินตอบ "ใช่" ก่อนทุกครั้ง (เป็นคำสั่ง ไม่ใช่ล็อกในระบบ)
- token แบบ "อ่านอย่างเดียว" (สร้างที่ Settings → MCP) มองไม่เห็นเครื่องมือสั่งงาน

## ความปลอดภัย

- คำขอทุกตัวเซ็น HMAC-SHA256 (header `X-DA-Site`, `X-DA-Timestamp`, `X-DA-Nonce`, `X-DA-Signature`) และ nonce ใช้ได้ครั้งเดียว
- relay ส่งต่อได้เฉพาะ `https://<โดเมนสาธารณะ>/?rest_route=/doaction-care/v1/wake` และต้องมีลายเซ็นของ relay แยกอีกชั้น relay ไม่ถือรหัสลับของเว็บ
- ปลั๊กอินรุ่นใหม่ต้องมีลายเซ็น Ed25519 (private key อยู่ที่ `~/.config/doaction-care/signing.key` ไม่อยู่บน Cloudflare)
- ไม่รองรับ WordPress multisite (ไม่ทำอะไร)
- ใช้ lock เดียวกับระบบอัปเดตอัตโนมัติของ WordPress จึงไม่ทำงานซ้อนกัน

## การปล่อยเวอร์ชันและ deploy

```bash
# portal (build ก่อนทุกครั้ง)
npm run deploy

# ปลั๊กอิน: แก้ Version ใน doaction-care.php (หัวไฟล์ + DOACTION_CARE_VERSION) แล้ว
node scripts/release-care-plugin.mjs
```

- สคริปต์ปล่อยปลั๊กอินจะเซ็น zip, อัปโหลดไป R2 (`care-plugin/`) และคัดลอกไปที่ `wp-plugin/doaction-care.zip` (commit ไฟล์นี้ด้วย)
- เว็บจะไม่อัปเดตปลั๊กอินเอง แอดมินต้องติ๊ก "Do Action: Care" ในรายการอัปเดตของแต่ละเว็บ
- migration ใหม่ต้องรัน**ก่อน** deploy: `npx wrangler d1 execute DB --remote --file migrations/<ไฟล์>.sql`

### relay บน OVH
- รันเป็น container `wake-relay` ข้าง Caddy ของ PDPC (`/opt/pdpc/deploy/Caddyfile`)
- ติดตั้ง/อัปเดต: `bash relay/install-ovh.sh`, เพิ่มชื่อ sslip.io: `bash relay/add-sslip-host.sh`
- secret ฝั่ง portal: `WAKE_RELAY_URL`, `WAKE_RELAY_SECRET` (ลบทั้งคู่เพื่อกลับไปปลุกตรงจาก Worker)
- รายละเอียดเพิ่มเติม: [relay/README.md](../relay/README.md)

## แก้ปัญหาที่พบบ่อย

| อาการ | สาเหตุที่เป็นไปได้ | ทำอย่างไร |
|---|---|---|
| งานรอคิวนาน | ปลุกไม่สำเร็จ, เว็บคนเข้าน้อย | ดูข้อความใต้แถวเว็บใน `/admin/sites`, กด "ปลุกเว็บที่รอคิว" หรือกดปุ่มในหน้าตั้งค่าปลั๊กอิน |
| ปลุกไม่สำเร็จ `HTTP 403` | ไฟร์วอลล์ของเว็บบล็อก | ตรวจว่า relay ทำงาน (`curl -X POST https://51-79-223-252.sslip.io/wake` ต้องได้ `unauthorized`) |
